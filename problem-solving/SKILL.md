# Problem Solving

## 문제해결의 본질

> „Geduld zu haben gegen alles Ungelöste in Ihrem Herzen und zu versuchen, die Fragen selbst liebzuhaben wie verschlossene Stuben und wie Bücher, die in einer sehr fremden Sprache geschrieben sind."
> — Rainer Maria Rilke, *Briefe an einen jungen Dichter*, 네 번째 편지 (1903)
>
> 당신 마음속 풀리지 않은 모든 것에 인내를 갖고, 질문 그 자체를 사랑하려 애쓰십시오. 잠긴 방처럼, 아주 낯선 언어로 쓰인 책처럼. (자체 번역)

이 스킬이 호출되는 시점의 문제는 이미 한 번 살아남은 문제다. 사용자는 대개 위에서 아래로 훑는 탐색을 해봤고, 그게 통하지 않았다. 그러니 뻔한 첫 수(로그를 확인하세요, 배치를 줄여보세요)를 다시 두는 것은 수가 아니다. 이미 실패한 길이라는 사실 자체가 정보다.

문제는 고쳐야 할 증상이 아니라 아직 이해하지 못한 현상이다. 여러 곳에서 사소한 증상이 반복된다면, 그것들을 한꺼번에 낳는 본질적인 출발점이 있다. 증상 하나하나를 막는 해결은 같은 문제를 다른 모습으로 다시 만나게 할 뿐이다.

해결은 지략이다. 같은 문제도 어디서 바라보느냐(Lens)에 따라 다른 문제가 되고, 어떤 수를 두느냐는 곧 어떤 믿음에 거느냐다. 좋은 수는 성공했을 때 문제를 풀고, 실패했을 때도 다음 Lens를 정할 정보를 남긴다.

## 입력: 시작에 필요한 최소한

반드시 필요한 것은 두 가지다. 이 둘이 없으면 한 번에 묻고, 있으면 바로 시작한다.
- **무엇이 안 되는가**: 기대와 다르게 일어난 현상 한 문장. 예) "학습 중 계속 OOM이 난다"
- **그게 어디에 있는가**: 코드 경로나 저장소. 코드가 없는 문제라면 아이디어·설계 설명. Blueprint의 재료다.

정렬 스프린트에서 채우는 것. 요청에 없으면 정렬의 결정 요청 하나로 한꺼번에 묻고, 모른다고 하면 비운 채로 간다.
- **이미 해 본 것**(닫힌 길). 없다면 이 스킬의 전제—이미 한 번 살아남은 문제—가 아직 서지 않은 것이므로, 정렬 스프린트에서 환경·버전·명백한 버그 같은 가벼운 점검부터 한다.
- **바꾸면 안 되는 것**(연구 주장, 베이스라인, 데이터 등). 가치 비교의 문제 보존도 축과 결정 요청 사유의 근거가 된다.
- **가진 자원과 기한**(GPU, 시간). 완주 가능성 축이 된다.

없어도 되는 것: 실행 모드(기본 검토형 + 중간 표시), 재현 명령(없으면 측정용 probe를 직접 만든다).

## 시작 전에

1. `config/values.yaml`을 읽는다. 각 단계에 들어갈 때 그 단계의 격언(maxim)을 먼저 읽고, 의도(intent)·허용 행동(licenses)·한계(guard)를 그 격언의 구체화로 이해한다. 지침이 다루지 않는 상황에서는 격언이 판단 기준이다. 격언을 사용자에게 매번 인용하지는 않는다. 격언은 보고서에서 각 단계의 머리말로 드러난다.
2. 실행 모드를 정한다. 사용자가 이미 밝혔으면 그대로, 아니면 한 번만 묻는다.
   - 자율성: `검토형`(결정 요청을 보이고 응답을 기다림) / `자율형`(요청을 보이되 기다리지 않고 기본값으로 진행). 어느 쪽이든 사용자에게 묻는 것은 **결정 요청 사유가 있을 때뿐**이다. 사유와 무응답 시의 자율 결정 제한조건은 @references/autonomous-decision.md — 이 문서의 격언과 제한조건은 다른 단계의 지침보다 우선한다.
   - Blueprint의 쓰임: `중간 표시`(단계마다 Blueprint·테이블을 보여줌) / `결과 보고서`(탐색 경로 전체를 마지막에 정리)
   - 기본값: 검토형 + 중간 표시

중간 표시 모드에서는 결정 지점(Lens 이동, 후보 선택, 자식 Lens 진입·복귀)마다 Blueprint 명세를 갱신하고 `scripts/render_step.py`로 줌 캔버스 HTML을 만들어 사용자에게 보여준다. Lens의 경로(`lens_path`)는 코드의 처리 흐름을 따라 스스로 정하고 이동마다 이유를 단다. Lens 옆에는 스프린트가 진행된 만큼 카드가 순서대로 이어 붙는다: 지금 보는 곳 → 둘 수 있는 수 → 두면 생길 일 → 견주어 보기 → 바꿔 볼 수 있는 값 → 정해 주실 것. Lens 위쪽에는 후보들의 영향이 닿는 다른 프로세스의 블록을 꺼내 놓고, 후보를 고르면 영향이 닿는 곳까지 선이 흐른다. 이 명세들을 순서대로 쌓아둔 것이 그대로 결과 보고서의 데이터가 된다.

중간 개입은 사용자가 조절하는 자리이지만, 사용자에게 답을 요구하는 것은 결정 요청이 있을 때뿐이다. `scripts/quant.py decide`로 요청 사유를 판정하고, 사유가 있으면 명세의 `requests`에 질문·이유·선택지·무응답 시 기본값을 넣는다. 사유가 없으면 묻지 않고 진행하며, 캔버스는 근거를 보여주기만 한다. 사용자는 원하면 캔버스에서 Lens를 (범위 안에서) 옮기고, 가중치와 손잡이를 움직여 볼 수 있다. 그러니 보여주기 전에 사용자가 조절할 만한 것을 미리 계산해 둔다: 옮겨갈 만한 대안 Lens의 후보·테이블(`scopes`), 바꿔볼 만한 설정의 측정값(`knobs`), 가중치 민감도. 방법은 `references/quant-tools.md`. `[problem-solving 결정 응답]` 메시지가 오면 답한 요청은 그대로 따르고, 답하지 않은 고르기 요청은 기본값을, 채우기 요청은 다음 스프린트로 넘기며, 나머지 상태 변화(Lens 이동, 제외, 가중치)는 다음 루프의 입력으로 삼는다. `[새 시도 제안]`이 있으면 `scripts/sprint.py propose`로 등록하고, 다음 스프린트에서 후보로 올려 다른 후보와 똑같이 따진다.

## 프로세스

### 1. 정렬
사용자가 이 문제를 무엇으로 보고 있는지, 이미 무엇을 시도했는지를 먼저 확인한다. 문제를 먼저 사용자가 쓴 말과 틀 그대로 다시 적는다. 그가 서 있는 곳에서 시작해야 하기 때문이다. 그다음 관측(실제로 본 것)과 해석(그렇게 본 이유)을 분리하고, 사용자의 해석은 가설 후보로 넘긴다. 시도 이력은 "이미 닫힌 길" 목록이 된다. 정렬 결과는 모드와 관계없이 한 번 사용자에게 확인받는다. 잘못 정렬된 상태로 진행한 탐색은 전부 버려야 하기 때문이다.

### 2. 범위: 어디서부터 어디까지
- **심각성**: 이 문제를 방치하거나 잘못 고쳤을 때 생기는 결과의 경우의 수를 펼친다.
- **크기와 층위**: 반복적이고 본질적일수록 큰 문제다. 흩어진 사소한 증상들을 모아 공통 출발점 가설을 세우되, 그 가설이 묶인 증상 하나하나를 실제로 설명하는지 확인한다. 설명하지 못하는 증상은 다른 뿌리이므로 묶음에서 뗀다.
- 1단계에서 정렬한 문제를 Blueprint 위의 **문제 영역**(`problem`)으로 표시한다. Lens는 이 영역의 하위이거나 이 영역과 직결된 블록 안에서만 움직인다. 그 밖으로 가야 한다면 문제를 다시 정의하는 일이므로 사용자와 다시 맞춘다.
- Blueprint를 그리기 전에 **배치**를 정한다: 가로(한 방향으로 흐르는 짧은 파이프라인), 세로(단계가 많은 긴 순차 흐름, 코드를 위에서 아래로 읽는 구조), 격자(갈래가 많거나 독립된 모듈이 나란한 시스템). 코드와 문제를 보고 고르고, 고른 이유를 `layout_why`에 한 문장으로 남긴다. 기준은 `references/blueprint-and-lens.md`.
- 사용자 환경의 코드를 읽고 정보 처리 흐름대로 거시 Blueprint를 만든 뒤 (코드가 없는 문제, 예컨대 연구 아이디어나 설계 결정이라면 개념상의 정보 흐름—가정 → 방법 → 측정 → 주장—으로 블록을 세운다), 해결을 시도할 범위(Lens)를 블록 위에 긋는다. Blueprint 작성법은 `references/blueprint-and-lens.md`.

### 3. 깊이: 얼마나 들어갈지
Lens 안을 얼마나 잘게 분해할지 정한다. 좁힐수록 블록이 함수·클래스 → 코드 라인·텐서 흐름으로 펼쳐진다. 증상이 재현되고 국소적이면 깊이 들어가고, 같은 Lens 안의 해결이 경계만 미루며 반복된다면 깊이 대신 폭을 넓힌다(2단계로 복귀).

### 4. 후보 탐색
Lens 안에서 둘 수 있는 해결 후보를 찾는다. 순서는 다음과 같다.
1. 선행연구와 웹(논문, GitHub 이슈, 공식 문서, 포럼)에서 같은 문제를 다룬 사례를 찾는다.
2. 없다면 문제의 조건을 반사실적으로 조절해서(길이가 절반이라면? 프레임워크가 달랐다면? 도메인이 이미지였다면?) 인접 문제의 해법을 찾는다.
3. 그래도 없다면 직관적 후보를 세우되, 출처 없음으로 표시한다.

반사실적 확인은 경우의 수를 정량 비교할 근거를 주지만, 무제한으로 하면 가장 시간을 많이 잡아먹는 과정이다. 그래서 **검정 강도를 Lens 깊이에 맞춘다.** 거시 층위에서는 사고실험과 문헌 근거로 약하게, 미시 층위에서는 실제 수치를 바꿔 측정하며 강하게 검정한다(`scripts/quant.py`의 `sweep`·`scaling`·`leak`). 거시에서의 변경은 결과가 퍼져 있어 정밀 검정의 값어치가 낮고, 미시에서의 변경은 수치 단위라 싸고 정확하게 확인할 수 있기 때문이다.

모든 후보에는 출처와 그 방법이 통했던 조건을 붙이고, 근거는 사용자가 바로 열어 볼 수 있게 URL이나 내부 코드 위치·조각으로 단다. 그리고 이식가능성을 검토한다. 이식 문제가 크면 그 후보 안으로 자식 Lens를 열어 같은 프로세스를 재귀적으로 돈다. 상세는 `references/candidate-search.md`.

### 5. 경우의 수
각 후보를 선택했을 때 Lens 바깥 블록에서 달라지는 것들을 펼친다. Lens에 가까울수록 선명하게, 멀수록 흐리게 쓴다. 멀어질수록 예측의 확신도가 실제로 떨어지기 때문이다.

### 6. 가치 비교와 결정
후보들을 정량 테이블로 비교해 다음 수를 고른다. `scripts/quant.py table`로 종합 점수와 가중치 민감도를 계산하고, 1위가 가중치에 따라 바뀌면 사용자와 무엇을 중시할지 먼저 맞춘다. 바깥 파급과 이식 비용은 각 후보의 대가에 반영한다. 결정 요청 사유가 있으면 요청하고(검토형은 기다리고, 자율형은 기본값으로 진행), 없으면 1위로 진행하고 이유를 남긴다. 응답이 없을 때의 결정은 @references/autonomous-decision.md의 제한조건 안에서만 한다. 상세는 `references/value-table.md`.

## 설명과 정리

설명과 정리는 모든 단계를 가로지르는 작업이다. 캔버스의 문구, 「지금 상황」 오버뷰, 결정 요청, 보고서, 채팅 답변 모두 @references/writing.md를 따른다—격언과 함께 읽는다. 분명하게 쓰지 못하는 곳은 아직 덜 이해한 곳이므로, 문장을 다듬기 전에 이해하러 돌아간다.

Blueprint 바깥 왼편의 「지금 상황」은 매 스프린트 끝에 갱신한다(`overview`: 문제, 본 것과 해석, 이미 해 본 것, 지켜야 할 것, 확인된 사실, 다음). 현재 스프린트·가장 앞선 수·기다리는 것은 캔버스가 명세에서 스스로 채운다.

## 스프린트와 상시 표시

작업은 스프린트 단위로 사용자에게 보인다. 스프린트는 Claude가 스스로 선언한다: 단계가 바뀔 때, Lens를 옮길 때, 코드가 갱신됐을 때. 스프린트마다 단계·Lens 위치·목표 한 문장을 정하고, 끝날 때 요약과 확인된 사실을 남긴다(`scripts/sprint.py start/end`). Lens는 스프린트와 동기되어 "Sprint 3 · 탐색"처럼 표시되고, 지난 스프린트는 하단 기록에서 다시 열어볼 수 있다.

Blueprint는 코드가 갱신되는 주기에 맞춰 다시 만든다(`scripts/sprint.py blueprint`). 스프린트를 시작할 때마다 코드가 바뀌었는지(git 커밋, 파일 수정 시각) 확인하고, 바뀌었으면 Blueprint 버전을 올린다. 바뀐 블록은 "갱신"으로 표시되고, 사라진 블록을 가리키던 Lens·후보·파급은 경고된다.

캔버스는 상시 표시한다. 새 파일을 계속 만들지 않고 같은 캔버스를 제자리에서 갱신한다: 파일로 내는 환경에서는 같은 경로에 덮어쓰고, claude.ai에서는 같은 아티팩트를 링크로 갱신한다. 사용자가 하나의 화면을 띄워두고 스프린트가 쌓이는 것을 보게 하기 위해서다.

## 루프와 종료

6단계의 결정 후, 결과나 새 정보에 따라 2~6단계로 돌아간다. Lens를 넓히거나, 좁히거나, 자식 Lens에서 부모로 복귀한다.

멈출 때를 횟수로 정하지 않는다. 문제마다 필요한 루프 수가 다르기 때문이다. 대신 각 루프와 각 자율 행동이 **무엇을 바꿨는지**를 기록하고, 바뀌는 양이 줄어들면 멈춘다. 더 모아도 결정이 바뀌지 않는다는 것이 곧 정보가 충분하다는 뜻이다. 변경량 계산과 절단 기준은 `references/value-table.md`의 "변경량 기반 절단"이고, `scripts/quant.py delta`로 계산한다.

- **루프 절단**: 결정 단계(탐색·경우의 수·결정) 스프린트의 변경량이 두 번 연속 1 이하이면 끝내고 보고한다(`sprint.py end`가 판정). 정렬·범위·깊이 스프린트는 문제를 정의하는 단계라 절단 판정에 넣지 않는다—테이블이 바뀌지 않아도 문제 정의와 측정이 바뀌는 것이 그 단계의 일이다.
- **행동 절단**: 한 단계 안의 자율 행동(검색, 코드 읽기, 측정)이 연속 3회 새 사실을 내지 못하면 그 단계를 닫는다.
- **분석 한계**: 남은 불확실성이 검색·분석으로는 줄지 않고 실행해야만 풀린다면 끝내고, 그 실험을 다음 수로 넘긴다.
- **재귀 복귀**: 자식 Lens의 변경량이 부모 결정을 흔들지 못하는 수준으로 떨어지면 부모로 돌아간다.

절단은 실패가 아니다. 보고서에 어느 기준으로 멈췄는지와, 멈춘 시점에 남아 있던 변경의 흐름을 함께 남긴다.

## 보고
결과는 **단일 인터랙티브 HTML 페이지**로 낸다. 탐색 중에 보여준 Blueprint·Lens·후보·파급·가치 테이블이 모두 페이지 안에서 다시 조작 가능해야 한다. 사용자가 Lens를 클릭해 펼치고, 버린 후보를 다시 열어보고, 테이블을 다시 정렬할 수 있어야 한다. 형식은 `references/report-template.md`. 결론만이 아니라 거쳐 간 Lens, 버린 후보와 버린 이유, 남은 불확실성을 함께 남긴다. 버린 길의 기록은 다음 문제에서 같은 길을 다시 걷지 않게 해준다.
